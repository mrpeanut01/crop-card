# Phase 36: heavy exports off the request path, and two phones editing the same thing

Started and finished 2026-10-02 (36 ✓). Phase 36 takes the two platform items left after Phase 34. It runs as one sprint, 36, alongside Phase 35. No safety rule changes, so `RULES_VERSION` stays 0.7.1. The CLAUDE.md invariants bind it, especially invariant 3 (single replica only), invariant 4 (spray records immutable after the lock window) and invariant 6 (tenant isolation).

## 36: render exports in a worker, and catch conflicting edits from two devices

### PDF and export rendering off the event loop

The app runs on one Node event loop at 0.5 vCPU, and the capacity review in CLAUDE.md names PDF and export rendering as the next lever. pdfmake renders on the main thread in `lib/server/pdf.ts`, `lib/records/treatmentLogPdf.server.ts`, `lib/records/yearSummaryAnimalsPdf.ts`, `/api/records/year-summary.pdf` and `/api/spray/records/export.pdf`, and the certifier pack and `export.zip` build large files in process. While one of those runs, every other farmer waits.

Move the rendering into a `node:worker_threads` worker. The request handler still does every database read, tenant check and permission check on the main thread, as today, and hands the worker only plain data plus the document definition. The worker never opens the database. Run one worker, started lazily and reused, with a small queue. Memory peaks near 510 to 650 MB of the 1 GiB container, so one worker is the ceiling, and a queue that is full answers 429 with `Retry-After` in both languages. Output must be byte-identical or render-identical to today's, so VDACS integrity hashes and the existing export tests still hold. Measure event-loop delay during a large export before and after, with the existing `[perf]` log, and record the numbers in the plan. The handoff fence (`scripts/handoff.mjs`) must still drain in-flight renders before a deploy hands over.

#### As built (render-worker)

Every compliance PDF (spray, VDACS, year summary, animal treatment log, certifier pack summary), the certifier pack's README and CSV files, and the bytes of `export.json` (for `GET /api/account/export.json` and `export.zip`) are built by one render queue in `lib/server/render/`. Route code still does every database read, tenant check, permission check and VDACS hash on the main thread, then hands the queue a plain `PdfJobDoc` (header and footer as content with `{ $cc: 'page' | 'pages' }` placeholders, tables as `layout: 'ccTable'`). In production the jobs run in one lazily started `node:worker_threads` worker (`build/render-worker.mjs`, bundled by `scripts/build-render-worker.mjs` after `vite build`, with `env: {}` and a 384 MB old-generation limit); in dev and tests they run inline through the same executor and queue. One job runs, three wait, two per Owner; a full queue answers 429 `RENDER_BUSY` with `Retry-After: 15`, a render past 120 s or a dead worker 503, both as a page for a link click or as JSON, in English and Spanish. The handoff fence waits up to 30 s (`RENDER_DRAIN_TIMEOUT_MS`) for accepted renders and refuses new ones with the updating message. The pre-36 builders are frozen in `lib/server/render/__reference__/` and an equivalence test proves the new documents render byte for byte the same with the creation date pinned; a bundle test proves the worker pulls in no database, vault or SvelteKit runtime module.

Note: a process-wide `--max-old-space-size` in `NODE_OPTIONS` overrides the worker's `resourceLimits` (V8 flags are global). Production sets none, so the 384 MB limit holds there; the CI sandbox does set one, so the out-of-memory path is tested by terminating the worker instead.

### Two devices editing the same record

Offline sync is last-write-wins on the server. If two people on two phones edit the same task, planting or stock lot while offline, the later replay silently overwrites the earlier one. Most farm records are append-only and are not at risk: spray, insecticide, fungicide and harvest records are created once, locked after 48 h and voided rather than edited. The risk is in the endpoints that update an existing row (23 `PATCH` routes under `/api/**`).

For the rows that can be edited offline, carry the version the device last saw (its `updated_at`, or a version column if the decider rules one is needed) with the queued edit. On replay, a server whose row has moved on since then answers 409 `EDIT_CONFLICT` with both versions instead of overwriting. /records/pending then shows the conflict in plain words and lets the farmer keep theirs, keep the other, or, for simple fields, merge. Online edits that race in the same way get the same check. A change that only moves toward a safer state (closing a task, recording a discard) is never refused; the decider lists those cases. Hold-fact tables keep going through the hold guard, and nothing here may shorten a hold. Tenant scope is unchanged, and the cross-tenant test covers any new column.

The decider picks which tables and routes are in scope (what a farmer actually edits offline today), and whether a migration is needed.

#### As built (edit conflicts)

No migration and no Dexie version bump. `lib/edits/conflict.ts` (client-safe) holds the shared contract: `EDIT_FIELDS_BY_ACTION`, `sameEditValue`, `editConflicts` and `isEditConflictBody`. `PATCH /api/crops/:id` (`edit-details`, `set-schedule`) and `PATCH /api/tasks/:id` (`edit`, `reschedule`, `assign`) take an optional `base`, the value of each changed field as the device last saw it; `runCheckedEdit` in `lib/server/editConflict.ts` re-reads, compares and writes in one `writeRecord()` transaction, and a field that moved on to a third value refuses the whole edit with 409 `EDIT_CONFLICT`, the conflicting fields and every editable field as stored now. Both routes replay through `withClientRecordId` (a 409 releases the claim), `set-schedule`'s task re-anchoring and seed-start tasks now run in the same transaction, and closing a task or changing a planting status never reads `base`. On the client a new `record-edit` queue kind (`lib/edits/queue.ts`, sent as a `PATCH`) carries the /plan edit modal's two requests when the network drops, a 409 parks the row with its `editConflict`, and `EditConflictChoice.svelte` on /records/pending and inside the modal offers Keep mine, Keep theirs and Choose for each (`rebaseEdit` in `lib/edits/resolve.ts`, `resolveEditConflictForActiveOwner`). A 404 on a queued edit says the planting was deleted on another device. Tests: shared contract unit and fast-check tests, `editConflict.properties.test.ts` (random two-device interleavings on real SQLite), `editConflict.crossTenant.test.ts` (another Owner's id is always 404, never 409), route tests, and the two-context e2e specs `edit-conflict.spec.ts` and `edit-conflict-api.spec.ts`.

## 36 rulings

Binding decisions for sprint 36 (section "36" above). Three clusters built in parallel: **render-worker**, **edit-conflicts** (server) and **conflict-ui** (client). Where a ruling and the plan disagree, the ruling wins; where the CLAUDE.md invariants and a ruling disagree, the invariant wins. No safety-rule changes: `RULES_VERSION` stays 0.7.1.

What the code looks like today, which these rulings rest on:

- Every renderer goes through `renderPdf()` in `lib/server/pdf.ts`, which calls pdfmake on the main thread. The callers are `/api/spray/records/export.pdf`, `/api/records/export.vdacs.pdf`, `/api/records/year-summary.pdf`, `lib/records/treatmentLogPdf.server.ts` (behind `/api/animals/treatments.pdf` and the organic pack) and `lib/server/organicPack.ts` (the pack summary). Each document definition holds functions: `header` and `footer` callbacks, and the `fillColor`/`hLineColor`/`vLineColor` table layout. Functions cannot be posted to a worker.
- The VDACS integrity hash is a SHA-256 of the row set, computed from database rows before rendering. It does not depend on the PDF bytes.
- `export.zip` runs `JSON.stringify(payload, null, 2)` on the main thread and streams vault files through `zipStream`. The organic pack builds the README, the summary PDF and seven CSVs in memory, then streams them with any vault files.
- None of the 23 `PATCH` routes is queued offline today. Every offline queue kind is a `POST` that creates or appends a row. The only queued kinds that change an existing row are `task` (closing, which only moves toward done) and `seed-start` (where the latest `observedAt` already wins). So two-device edit conflicts happen today only online, from a form that was open while someone else saved, and Phase 36 adds the first queued edits.
- `crops` (plantings) and `tasks` have no `updated_at` or version column. Neither is a hold-fact table.

#### C-E1 (owned by edit-conflicts; conflict-ui imports it)

`src/lib/edits/conflict.ts`, client-safe with no server imports. Write it exactly to this signature. If conflict-ui needs it before edit-conflicts lands, it writes an identical copy, and edit-conflicts' version wins at integration.

```ts
export const EDIT_CONFLICT_CODE = "EDIT_CONFLICT" as const;
export type EditTarget = "planting" | "task";
export type PlantingEditField =
  | "varietyDisplayName"
  | "quantityPlanted"
  | "quantityUnit"
  | "harvestUseCases"
  | "plantingDate"
  | "blockId";
export type TaskEditField =
  "title" | "body" | "scheduledFor" | "assigneeUserId";
export type EditField = PlantingEditField | TaskEditField;
export type EditValue = string | number | null | readonly string[];
export type EditValues = Partial<Record<EditField, EditValue>>;
export interface EditConflictField {
  field: EditField;
  base: EditValue;
  mine: EditValue;
  theirs: EditValue;
}
export interface EditConflictBody {
  error: string;
  code: typeof EDIT_CONFLICT_CODE;
  target: EditTarget;
  id: string;
  action: string; // the PATCH body's action
  fields: EditConflictField[]; // conflicting fields only
  current: EditValues; // every in-scope field of the row as stored now
}
/** action key `${target}:${action}` → fields that action can change. */
export const EDIT_FIELDS_BY_ACTION: Readonly<
  Record<string, readonly EditField[]>
>;
// 'planting:edit-details' → varietyDisplayName, quantityPlanted, quantityUnit, harvestUseCases
// 'planting:set-schedule' → plantingDate, blockId
// 'task:edit' → title, body; 'task:reschedule' → scheduledFor; 'task:assign' → assigneeUserId
export function sameEditValue(
  a: EditValue | undefined,
  b: EditValue | undefined,
): boolean;
export function editConflicts(
  base: EditValues,
  mine: EditValues,
  current: EditValues,
): EditConflictField[];
export function isEditConflictBody(x: unknown): x is EditConflictBody;
```

Request side: each in-scope Zod variant gains `base: editBaseSchema.optional()`. That is a strict object of the action's own fields, each optional, typed as in the variant but nullable. Edit-conflicts owns those schema edits, the regenerated `static/openapi.json` and the `recui.editConflict.error` key. Dates are epoch ms on both sides, and `scheduledFor`/`plantingDate` in `current` are epoch ms (or `null`).

#### Shared-file etiquette

- `catalogs/{en,es}/records.ts` is edited by all three clusters. Each adds only its own prefix (`recui.render.*`, `recui.editConflict.*`, `recui.conflict.*`), in sorted position, and never moves existing keys.
- Only render-worker edits `PHASE_36_PLAN.md` and `package.json` scripts. Nobody edits `CLAUDE.md`; the phase bullet is written at integration.
- No migration and no Dexie version bump in this sprint. A cluster that thinks it needs one stops and raises it.
