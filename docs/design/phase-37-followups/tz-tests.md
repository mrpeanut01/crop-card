# Unit tests that failed outside UTC (cluster T)

On `main` at `8462010f`, `TZ=America/New_York pnpm exec vitest run` failed 25 tests in 6 files. Sydney failed the same files plus one in `tests/unit/sourceDrift.test.ts`, which only fails east of UTC. CI and production run in UTC, so neither saw it. Frost dates, planting dates and other calendar days are stored as UTC midnight, and each failure read or built one of those in the process zone.

## Production effect

None in production, which runs in UTC: every changed function returns the same values there. In a non-UTC process (a developer machine, or the browser for `plantingWindow` through `NewPlantingModal`):

- `formatDateMs`, `calendarDay` and `frostDatesIsoForYear` gave the day before each frost or planting date west of UTC, so the planting-window route, the planner prompt and `/plan`'s frost dates would have been a day early.
- The schedule's tomorrow floor was not a calendar day. East of UTC, `plantingWindow` printed it as today.
- Hard-frost dates were off by the zone offset against the light-frost dates they are compared with.
- `check-source-drift.mjs` run by hand east of UTC dated PPLS transfers and status changes a day early in the drift issue. The weekly job runs in UTC.

## Not changed

- The engine still uses the process zone when no `timeZone` is passed, and no production caller passes one yet. Passing the farm zone from the server loaders changes behaviour, so it belongs in its own PR.
- `rolloverDateForSeason` and `suggestPlanningYear` (`lib/season/planningYear.ts`) still build the rollover at process-local midnight while planting dates are UTC midnight. Nothing failed, but west of UTC a planting dated on the rollover day reads as the earlier season.

## Guard

`pnpm --filter @cropcard/web test:unit:tz` runs the suite with `TZ=America/New_York` (documented in `docs/ci.md`). `ci.yml` has no non-blocking job pattern (the visual screenshots are a separate on-demand workflow), so CI is unchanged.
