# #871: watch-deploy.sh behind a proxy that refuses production

## Problem

`scripts/watch-deploy.sh` confirms a deploy by fetching production's `/api/health` and printing the LIVE banner once `version` is the merged commit (or a newer main commit containing it). In a Claude Code cloud session the network proxy refuses CONNECT to `app.cropcard.io` (403), so the fetch never succeeds and the script waited out its 30-minute loop.

## Ruling

Option 2 from the issue (coordinator, 2026-10-20): when the proxy refuses the tunnel, trust the deploy workflow's own health check and print a distinct banner.

## What the deploy workflow checks

`deploy.yml` runs `scripts/deploy-azure.sh --apply --ci` with `CROPCARD_SHA` set to `github.event.workflow_run.head_sha` (the commit `ci` passed on) or `github.sha` for a manual dispatch. With `--apply`, that script's only `exit 0` comes after `/api/health` at the deployed origin reports exactly that SHA as `version`; it exits 1 after 40 tries otherwise, and a dirty tree is refused in CI. A run whose job is skipped concludes `skipped`, not `success`. So a green deploy run means production served the commit that run deployed.

The catch: the Actions API labels a `workflow_run` run with main's newest commit (`head_sha`), not the commit it deploys. Run 260 on 2026-10-17, for example, deployed 283e2de but is labelled 4184884. A green run "for this SHA" cannot be found from `head_sha`.

## Changes

- `deploy.yml` sets `run-name: deploy ${{ github.event.workflow_run.head_sha || github.sha }}`, the same expression as the job's `SHA`, so each run's `display_title` names the commit it deployed.
- `watch-deploy.sh` now probes `/api/health` with `-w '\n%{http_connect}'`. A proxy refusal is curl exit 56 (22 with `--fail` on newer curl builds, seen with curl 8.7.1) together with a 4xx or 5xx `%{http_connect}`, which is 000 without a proxy and 200 once a tunnel opens. On the first refused attempt the script stops calling curl and polls the deploy runs instead:
  - a green run titled with this commit, or with a newer commit that the compare API says contains it (only runs created since CI finished, to bound compare calls), prints `✅  LIVE IN PRODUCTION (health check by the deploy workflow)` with the origin marked "(this machine cannot reach it)", logs the run URL, and exits 0;
  - a failed or timed-out run titled with this commit, or any created since CI finished (the existing rule), exits 1;
  - nothing green within the same 30 minutes exits 1 with "no green deploy run".
- Every other failure (timeout, DNS, 5xx from the app, a receive error without a proxy, an older version, a failed deploy while the app is reachable) takes the unchanged path.
- Runs titled the old way (`deploy`) never count as green for the fallback, so the fallback only works for deploys made after this change.
- `CLAUDE.md` ("Shipping and deploys") and `docs/ci.md` say the fallback banner counts as live, and why.

## Tests

`apps/web/src/lib/server/ops/watchDeployScript.test.ts` runs the real script with stub `gh` (fixtures through `jq`, as `gh --jq` does), `curl`, `sleep` and `seq` (capped loops) on `PATH`: the normal live path, the fallback through exit 56 and 22, waiting on a run in progress, a newer commit accepted and an older one refused, failed runs, four non-proxy failures that keep today's behaviour, an older version, and a failed deploy with the app reachable. It needs `jq` (skipped locally without it, never on CI).
