### CT-001 — Spray record always fails with 500 (FK constraint on sprayers vs equipment) [P1]
- **UC:** UC-02
- **Route:** /spray → POST /api/spray/record
- **Expected (per use-cases.md UC-02 step 8–9):** After clicking "Confirm — record this spray", a spray record is persisted server-side and the user lands on a success card with next-actions (Today / Records / Plan another).
- **Observed:** Every attempt to confirm results in `POST /api/spray/record → 500 Internal Server Error`. The server log shows `SqliteError: FOREIGN KEY constraint failed` in `insertSprayEvent` at `sprayEvents.ts:95`. Root cause: `spray_events.sprayer_id` has a FK referencing `sprayers(id)`, but sprayers are stored in the `equipment` table (Phase 8a migration). `listSprayers()` in `$lib/db/sprayers.ts` reads from `equipment` filtered to `type='sprayer'`; the equipment IDs shown in the UI (e.g. `05ca5057...` for Sprayer-Clean) are not present in the `sprayers` table (which is empty). The FK cannot be satisfied. No record is ever persisted. Success criterion — "Spray record persisted (server or queue) within 48-hour lock window" — is never met.
- **Console:** `[ERROR] Failed to load resource: the server responded with a status of 500 (Internal Server Error) @ http://localhost:5273/api/spray/record`
- **Network:** `[POST] http://localhost:5273/api/spray/record => [500] Internal Server Error`
- **Server log:** `SqliteError: FOREIGN KEY constraint failed` → `at Module.insertSprayEvent (/app/apps/web/src/lib/db/sprayEvents.ts:95:6)` → `at POST (/app/apps/web/src/routes/api/spray/record/+server.ts:209:21)`
- **Screenshot:** ./screenshots/2026-05-23-UC-02-CT-001.png
- **Recommendation:** The `spray_events.sprayer_id` FK currently points to `sprayers(id)` (legacy table, now empty). Since Phase 8a migrated sprayer data to `equipment`, either (a) update the FK in `spray_events` to reference `equipment(id)` and run a migration, or (b) populate `sprayers` via a backfill migration that mirrors relevant `equipment` rows. Option (a) is cleaner given the documented Phase 8a intent. The seed script (`seed-test-data.mjs`) inserts into `equipment`, not `sprayers`, confirming the schema FK is stale.
- **Cross-ref:** No prior audit finding (new).

### CT-002 — Silent failure: no UI error shown when spray record POST returns 500 [P1]
- **UC:** UC-02
- **Route:** /spray — client-side `recordSpray()` in `+page.svelte`
- **Expected (per use-cases.md UC-02 Success):** Spray record persisted or queued; user lands on success card or sees a clear error if persistence fails.
- **Observed:** When `POST /api/spray/record` returns 500, the page stays on the spray form with no user-visible error message. The `recordOutcomes` map is populated with `{kind:'failed', error:'HTTP 500'}` for the block, but the per-block status list (`.per-block-status`) is only rendered when `selectedBlocks.length > 1`. For single-block flows, `lastError` is never set by `recordSpray()`, so the `<p class="error" role="alert">` at line 722 never renders. The `Confirm` button remains clickable; the user has no indication the operation failed and no way to diagnose the problem.
- **Console:** 2x `[ERROR] Failed to load resource: the server responded with a status of 500`
- **Network:** 2x `[POST] http://localhost:5273/api/spray/record => [500] Internal Server Error`
- **Screenshot:** ./screenshots/2026-05-23-UC-02-CT-001.png (same page state after two failed confirms)
- **Recommendation:** In `recordSpray()` (around line 508 in `+page.svelte`), after populating `recordOutcomes`, set `lastError` if any outcome has `kind === 'failed'` and `recordedId` is still null. Alternatively, the per-block status block guard at line 876 (`selectedBlocks.length > 1`) should also trigger when any outcome is `'failed'`, regardless of block count.
- **Cross-ref:** No prior audit finding (new).

### CT-003 — Wind / temp / rain condition steppers absent; "Check safety" CTA missing [P2]
- **UC:** UC-02
- **Route:** /spray
- **Expected (per use-cases.md UC-02 step 5–7):** Step 5 — "Adjust conditions via steppers — wind, temp, rain, optional corn height". Step 7 — "Check safety (sticky CTA at bottom)".
- **Observed:** The spray page contains no wind, temperature, or rain input controls. Only the corn-height stepper (corn block specific) is present. No "Check safety" button exists. The spec prose in the UC explicitly lists these as primary-path steps. The implementation uses conservative fixed defaults (wind=5 mph, temp=70°F, rain=0 mm) set at Svelte state initialization (lines 37–39) and runs the safety kernel automatically via a debounced `$effect` (noted in an inline comment at line 691 of the source). The UI gives operators no way to input actual field conditions, which may cause the kernel to approve sprays it would reject under true conditions (e.g. wind > threshold for a volatile product).
- **Console:** none
- **Network:** none
- **Screenshot:** ./screenshots/2026-05-23-UC-02-CT-001.png
- **Recommendation:** The Phase 21b follow-up comment at line 691 documents this intentional removal. Update the UC-02 spec to reflect the current design (no condition inputs; kernel uses fixed defaults), or restore the steppers if the product decision was reversed. If retained as-is, expose the defaults to the user ("Using: 5 mph wind, 70°F, no rain forecast") so they can judge applicability.
- **Cross-ref:** Spec divergence — may reflect deliberate Phase 21b design change not yet reflected in `docs/use-cases.md`.
