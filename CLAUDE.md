# CropCard — agent guidance

This file is read by Claude Code (and similar agents) on every session in this repo. Keep it short and actionable.

## What this project is

CropCard is an offline-first PWA replacing the paper "Field Card" for a small-plot Loudoun County, VA farm. SvelteKit + TypeScript, single container, deployed to Azure Container Apps with SQLite + Litestream.

## Invariants — DO NOT BREAK

1. **Safety rules live in `apps/web/src/lib/safety/`.** Plugin JSON files cannot override them. Adding a new rule means editing TypeScript, bumping `RULES_VERSION` in `apps/web/src/lib/safety/version.ts`, and writing exhaustive vitest + fast-check tests.
2. **Plugins are data-only.** No executable JavaScript in any file under `plugins/`. Schema validation at registration is mandatory.
3. **Single replica only.** `infra/azure/main.bicep` sets `maxReplicas: 1` and `revisionMode: 'single'`. SQLite + Litestream is single-writer; multi-replica would corrupt the DB. Do not change these without a database migration plan.
4. **Spray records are immutable after the lock window** (default 48h, FR-09). Server endpoint must enforce this regardless of UI.
5. **Helper role cannot edit locked records or override custom rates.** Server enforces in addition to UI.
6. **Tenant isolation is row-level via `owner_id`** (Phase 18a). Every tenant-scoped repo MUST funnel reads/writes through `tenantWhere`, `withTenant`, or `tenantValues` from `apps/web/src/lib/db/tenant.ts`. The `TenantScoped` brand on schema tables is the compile-time gate; the cross-tenant property test (`apps/web/src/lib/db/tenant.crossTenant.test.ts`) is the runtime gate. Adding a new tenant-scoped table requires: (a) brand it via `tenantScoped(...)` in `schema.ts`, (b) add an `owner_id` column + composite index, (c) wire it into the cross-tenant test, (d) refactor consuming repos. Intentionally-global queries must call `unscopedQueryNote('reason')` in the same function.
7. **AI assists, never gates** (Phase 25 v2 design addendum). Every pre-populated value carries a `provenance` tag (`plugin | data | ai | manual | fallback`) rendered with the `Provenance` component. No-key is a first-class product mode, not an error state — the deterministic fallback path must work end-to-end without an Anthropic key. The `aiTry()` helper at `apps/web/src/lib/server/aiTry.ts` is the _only_ place AI degradation conditions (`no-key | over-cap | offline | rate-limit | timeout`) are checked; every endpoint that _could_ call Claude goes through it. Lot # is never `ai` — always `manual`. Design source-of-truth: [`docs/design/almanac/AI_PROVENANCE_ADDENDUM.md`](docs/design/almanac/AI_PROVENANCE_ADDENDUM.md).
8. **One inventory chrome** (Phase 27, design ratified 2026-05-26). Every inventory-bearing surface — pesticide, fertility, seed, crop plugin, sprayer — funnels through the same `List → Detail → Edit/Add → List` pattern with a 5-chip type swap on the list. Per-type _fields_ differ; per-type _chrome_ does not. Crop archetype is a first-class explicit enum on the plugin (`archetype: small-grain.zadoks | row-grain.pollination | dry-seed-legume | winter-squash-cure | continuous-harvest-fruit | cut-and-come-again-leafy | cover-crop.termination | forage-cutting-cycle | perennial-vine-quality | tree-fruit-multi-pick`), NOT inferred from a 5-field combo at render time. The 5-method add flow (barcode · label OCR · AI photo · search · manual) is preserved but routes through the type-aware canonical form, so every entry method writes the same audit/hash-chain row. Stock = lots on hand (instances); Catalog = plugin definitions; the unified surface toggles between them via a segmented control. **Authz: helpers can read every inventory view (`/inventory`, `/inventory/[type]/[id]`); mutations gate at the API layer (`/api/stock/**`, `/api/equipment/**`, `/api/plugins/**`). Pre-Sprint-9 the legacy `/settings/plugins` + `/settings/sprayers` shells gated viewing at `role==='owner'`; Sprint 9 made viewing helper-visible by design (#277) so a helper can scout the same inventory the owner sees without a 403 dead-end.** Design source-of-truth: [`docs/design/almanac/INVENTORY_UNIFICATION.md`](docs/design/almanac/INVENTORY_UNIFICATION.md) + [`direction-almanac-inventory.jsx`](docs/design/almanac/direction-almanac-inventory.jsx) (15 artboards). Open [`docs/design/almanac/inventory-unification-preview.html`](docs/design/almanac/inventory-unification-preview.html) in a browser to walk the prototypes.

- **EPA registration numbers** ([#381](https://github.com/mrpeanut01/crop-card/issues/381)). 67 of the 109 missing `epaRegistrationNumber`s were filled from EPA PPLS label URLs whose title names the product (provenance per plugin in `apps/web/scripts/epa-reg-sources.json`); the fungicide schema now carries the field (it was being stripped, so every fungicide export row read `MISSING_EPA_REG`). The remaining 42 (15 generic/exempt/test plugins, 27 ambiguous or unmatched brands) are allowlisted with reasons in the #255 coverage gate, which now also fails CI on a new pesticide plugin without a number. Those 27, plus the 164 `formulation`/`defaultUnit` gaps from #255, need a label on hand, not guesses.
- **Migration runner.** `db:migrate` uses `node scripts/migrate.mjs` (disables FKs around `migrate()` because SQLite ignores `PRAGMA foreign_keys=OFF` inside a transaction and drizzle wraps each migration file in one). Use the wrapper, not bare `drizzle-kit migrate`.
- **ESLint rule adoption** is done except two rules left off on purpose, with the reason inline in `apps/web/eslint.config.js`: `svelte/no-navigation-without-resolve` (no `kit.paths.base`, so `resolve()` changes nothing) and `svelte/prefer-svelte-reactivity` (flags local temporaries and copy-then-reassign `$state` updates, not real reactivity bugs). Revisit the first if a base path is ever set. `cropcard/no-raw-tenant-table` still treats a module-level helper call as covering the whole file.
- **Label research** (EPA numbers, pollinator classes, rainfast intervals, formulation/unit gaps, organic compliance flags) needs primary label sources the cloud environment can't open. A ready-to-run brief for a local agent is at [`docs/research/label-research-prompt.md`](docs/research/label-research-prompt.md).
- **Weather-model limits.** Leaf wetness is an RH ≥ 90% proxy and the `/plan/wheat` FHB panel is a proxy for the national scab model (no public API). Past hourly weather is not stored, so vernalization before the forecast window uses Dulles climate normals. NEWA station integration would replace both proxies. Only 7 fungicide plugins carry a sourced `rainfastHours` (sources in `apps/web/scripts/epa-reg-sources.json`); the rest fall back to the 4 h default in the dry-window gate.
- **Draw your farm.** `/plan` sends an owner whose farm has no blocks to `/plan/farm` (any query string, e.g. `?setup=skip`, stays on `/plan`). It hosts the same `FarmMapEditor` as `/settings/farm/map`, which now has a Map / Dimensions toggle. Dimensions store `width_ft`/`length_ft` on `fields` and `blocks` (migration 0049) and draw them as auto-packed boxes; that layout is illustrative and never feeds geometry consumers (pollination distance, shade, weather centroids). The map centers on the browser's location when nothing is drawn yet, plus a Center on my location button.
- **Plugin farm copies** cannot be reverted to the shared version (re-upload replaces the copy), and a farm copy that stops validating against a changed shared library is dropped from that Owner's view with a server warning.
- **Pollinator gate data.** The bloom attestation, its source and the gate verdict are stored on `insecticide_events` (migration 0046) and exported, and a one-mile nearby-blocks advisory flags bee-attractive or blooming neighbours. 17 insecticide plugins with unmapped active ingredients still fall back to legacy `pollinatorRisk`; classifying them needs label text this environment can't read.
- **Email-or-phone sign-in.** The landing form takes an email or a mobile number (`lib/identity.ts:parseIdentifier`). Email gets the magic link plus a 6-digit backup code in the same message (redeeming either burns both); a phone gets an SMS code, and an unknown number signs up a phone-only account. `users.email` is nullable since migration 0047, and `SessionPayload`/`AuthenticatedUser` carry `email: string | null` + `phone: string | null` (at least one is set). Use `identityLabel()` for display, never `user.email!`. Codes live in `login_codes` (HMAC-hashed, 5 attempts per code, per-destination and per-IP send limits) via `lib/server/loginCodes.ts`. Verified email/phone linking is at `/settings/account` → `/api/account/identity` (cookie session only; Bearer and impersonation are refused). Helper invites are still email-only, so a phone-only user must link an email before redeeming one.
- **Sync-queue conflict resolution** is last-write-wins on the _server_; multi-device same-spray race detection is not implemented (single-farm scope).
- **Orchard-specific seasonal calendar** (dormant spray, bloom fungicide). Orchards work as a kernel crop family today, but a richer calendar dataset is future plugin work.
- **AllocationWizard flows.** `components/wizard/allocation/wizardState.svelte.ts` (425 lines) is a facade that owns all shared `$state` and the public method surface; each async flow lives in `flows/` (`allocateFlow`, `allocationChat`, `scheduleFlow`, `commitFlow`, `draftFlow`, plus a pure `violations` humanizer). The AI-on chat send path, "Apply anyway" and the partial-failure commit path are covered by component tests only (no deterministic e2e trigger).
- **International / Canadian product equivalents.** The plugin library is US-label-anchored. EU/CA growers using the same active ingredients see different brand names (Liberty 200 SL vs 280 SL formulation; Roundup Transorb HC in Canada). Not a blocker for the Loudoun-VA primary persona.

## Shipping and deploys

- Finished work goes on its own branch off `main` → commit → PR → auto-merge (squash) once CI is green. Don't ask first.
- Merging to `main` deploys automatically: `ci` passes on the push → `.github/workflows/deploy.yml` builds the image (with `BUILD_SHA`) and runs `scripts/deploy-azure.sh --apply --ci`. That's the only deploy logic; the manual `./scripts/deploy-azure.sh --apply` runs the same path. The workflow succeeds only once production's `/api/health` reports the merged SHA as `version`.
- After a merge, run `./scripts/watch-deploy.sh <pr-number>` in the background. It waits for the merge, CI on `main` and the deploy, confirms the live `version`, then prints the `✅ LIVE IN PRODUCTION` banner. Relay that banner in chat only when the script prints it. A green workflow or a moved `main` is not "live". If it exits non-zero, report the reason and fix it.

## Code style

- Default to no comments; only add when the _why_ is non-obvious.
- TypeScript strict mode is on; do not weaken it.
- Field UI must be one-handed-glove operable (≥48dp tap targets, high-contrast).
- Test the safety kernel like a security boundary, not feature code.
