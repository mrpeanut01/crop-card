## Findings

### CT-001 — Upload rejection error not shown to user [P1]
- **UC:** UC-08
- **Route:** `apps/web/src/routes/plugins/+page.svelte` — "Advanced: upload raw plugin JSON" section
- **Expected (per use-cases.md UC-08 Primary path — Upload):** `/plugins` → upload JSON file → registry validates → loaded or **rejection with structured error**. The API endpoint at `POST /api/plugins/upload` does return a structured JSON body on 400: `{"error":"plugin failed schema validation","code":"schema","issues":[...]}`.
- **Observed:** After submitting junk JSON (`{"junk": "field", "notAPlugin": true}`) via the textarea + Upload button, the server correctly returns HTTP 400 with the structured issues list. However, the UI displays **no error feedback whatsoever** — no alert, no aria-live update, no toast, no inline validation message. The upload section remains unchanged and the user has no indication the submission failed.
- **Console:** `[ERROR] Failed to load resource: the server responded with a status of 400 (Bad Request) @ http://localhost:5273/api/plugins/upload`
- **Network:** `POST /api/plugins/upload → 400 Bad Request` — response body contains `{"error":"plugin failed schema validation","code":"schema","issues":[{"path":"...","message":"..."}]}` but body is not displayed.
- **Screenshot:** `./screenshots/2026-05-24-UC-08-upload-junk-no-error.png`
- **Recommendation:** In the upload handler on the client side, read the 4xx response body JSON and surface `issues[]` as an inline error below the textarea (e.g., `role="alert"` with `aria-live="assertive"`). The API already produces well-structured issue paths and messages.
- **Cross-ref:** Variant of the "silent failure on validation rejection" pattern; CLAUDE.md Invariant 2 requires "schema validation at registration is mandatory" — the server side is correct, but the invariant is undermined if the user never learns why their plugin was rejected.

### CT-002 — "Save plugin" button hidden under fixed bottom nav at mobile viewport [P2]
- **UC:** UC-08
- **Route:** `apps/web/src/routes/plugins/new/+page.svelte`
- **Expected (per use-cases.md UC-08 Primary path — Authoring):** `/plugins/new` → form-driven builder → **save** → registry validates → loaded. The save CTA must be reachable (CLAUDE.md: "Field UI must be one-handed-glove operable (≥48dp tap targets, high-contrast)").
- **Observed:** At 390x844 (iPhone 14 Pro), after selecting "Crop variety" and filling in the Display name field, the "Save plugin" button is positioned at `top≈667px` in the viewport. The primary nav bar is `position: fixed; top: 688px; z-index: 100` and extends to the bottom of the viewport. The nav bar physically overlays the Save button — the button label is not visible and Playwright's `browser_click` reported "nav subtree intercepts pointer events." The UC was completed via `element.click()` in evaluate, bypassing the interception.
- **Console:** No errors (the failure is a layout/pointer issue, not a JS error).
- **Network:** No network issue.
- **Screenshot:** `./screenshots/2026-05-24-UC-08-save-button-nav-overlap.png`
- **Recommendation:** Add `padding-bottom` equal to the height of the fixed bottom nav (approximately 130–150px on this viewport) to the main content area or the form's action row on `plugins/new`. Alternatively, ensure the Save/Cancel row uses `position: sticky; bottom: 0; z-index: 50` so it floats above the nav bar, making it always tap-reachable.
- **Cross-ref:** Likely affects other page-bottom CTAs at the mobile viewport. The `≥48dp tap target` policy in CLAUDE.md is met by the button itself (48px height observed), but the nav overlay makes the target unreachable.

## Infrastructure note (not a finding)
At startup, the Plugin Manager page reports "380 plugin file(s) failed to load" with "Unknown system error -35" for each file. Investigation showed these correspond exactly to new plugin JSON files that are **untracked in git** (present in `plugins/crops/` and other directories but not committed). The test container volume-mounts the host `plugins/` directory; the "error -35" is a macOS host filesystem I/O error (likely ENOLCK) for files that haven't been flushed/indexed on the volume. The 309 committed plugin files load correctly. This is not a schema validation or app code bug.
