### CT-001 — Decon endpoint does not clear `lastChemistryClass` [P1]
- **UC:** UC-04
- **Route:** `apps/web/src/routes/api/sprayers/[id]/decon/+server.ts` / `apps/web/src/lib/db/sprayers.ts`
- **Expected (per use-cases.md UC-04 Success):** `POST /api/sprayers/:id/decon` clears the chemistry flag. After a successful decon, `lastChemistryClass` should be null/unset on the sprayer record.
- **Observed:** The API returned HTTP 200 and updated `lastDeconAt` to the completion timestamp, but `lastChemistryClass` remained set to `"sulfonylurea"` in the response body and on subsequent page reloads. Verified via `GET /api/sprayers`: response included `"lastChemistryClass":"sulfonylurea"` and `"lastDeconAt":1779594221863` (deconAt > sprayedAt). A second POST to the decon endpoint confirmed the same: response body contained `lastChemistryClass:"sulfonylurea"` still set.
- **Root cause (read-only observation):** `apps/web/src/lib/db/sprayers.ts` line 66 calls `updateEquipmentState(id, { lastDeconAt: completedAt })` without including `lastChemistryClass: null`. The field is never nullified.
- **Impact:** The decon page at `/spray/decon?sprayer=<id>` continues to show "Last carried: sulfonylurea" after a completed decon. A user returning to the decon page will see the sprayer still appear as contaminated. The safety kernel (`crossContamination.ts`) correctly uses `lastDeconAt >= lastSprayedAt` and functions correctly — the kernel safety boundary is not broken. However the spec success criterion ("POST clears the chemistry flag") is not met.
- **Console:** No app errors during primary path.
- **Network:** `POST /api/sprayers/734f82f5-3ea4-4332-8655-fb2497821c51/decon` => 200 OK (response body retains `lastChemistryClass`).
- **Screenshot:** `./screenshots/2026-05-23-UC-04-CT-001.png` (decon page after reload showing "Last carried: sulfonylurea" on already-decontaminated sprayer)
- **Recommendation:** In `sprayers.ts` `recordDecon()`, also pass `lastChemistryClass: null` (or equivalent) to `updateEquipmentState`. The decon endpoint response should return the sprayer with `lastChemistryClass` absent/null to signal completion. The decon page should check `lastDeconAt >= lastSprayedAt` (as the kernel does) to decide whether to show the "Last carried" badge, rather than only checking `lastChemistryClass`.
- **Cross-ref:** Aligns with FR-05 decon requirement; safety kernel boundary is intact via `crossContamination.ts` `decontaminatedAfterLast` check.

### CT-002 — Top-bar decon banner does not disappear immediately after wizard completion [P2]
- **UC:** UC-04
- **Route:** `apps/web/src/routes/spray/decon/+page.svelte` / `apps/web/src/routes/+layout.svelte`
- **Expected (per use-cases.md UC-04 Success):** "top-bar banner disappears" after `POST /api/sprayers/:id/decon` succeeds.
- **Observed:** After clicking "Confirm complete" on Step 8, the success card ("✓ Decon recorded") appeared correctly. However, the top-bar `[role="status"]` banner — "⚠ 1 sprayer needs decontamination — Sprayer-Contaminated (sulfonylurea)" — remained visible on the same page. It only disappeared after navigating away to `/today` (which triggers a fresh SvelteKit layout server load).
- **Root cause (read-only observation):** `decon/+page.svelte` `complete()` function sets `completed = true` but does not call `invalidate()` or `goto()` after the POST succeeds (line ~115). The `+layout.server.ts` load function that populates `data.dirtySprayers` is not re-run within the same SPA navigation session.
- **Console:** No app errors.
- **Network:** POST returned 200. Banner stale data is a client-side rendering gap, not a server error.
- **Screenshot:** (captured in CT-001 screenshot — banner visible alongside success card)
- **Recommendation:** In `decon/+page.svelte`, after `completed = true`, call `invalidate('app:sprayers')` (or `invalidateAll()`) so the layout re-fetches `dirtySprayers`. Alternatively, call `goto('/spray')` which is already wired to the "Back to spray plan" button — that navigation naturally clears the banner.
- **Cross-ref:** P2 — does not block the primary path; the success card does appear and the POST succeeds.
