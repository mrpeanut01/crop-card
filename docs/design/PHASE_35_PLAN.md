## 35: one seed lot across several beds, and the AI paths end to end ✓

### Splitting one seed lot across beds

The layout engine (`apps/web/src/lib/layout/engine.ts`, `planFieldLayout` and `packSharedBeds`) still places a seed all or nothing inside one block. When the counted seed is bigger than every block the farmer picked, it places as many plants as fit in one block and reports the rest as left over, even when other picked blocks have room. The engine should spread one seed lot across several picked blocks before it reports anything left over.

What has to stay true:

- Each part of a split is a real planting on one block, at the plugin's spacing, so plant counts, harvest windows, pollination distances and the garden designer read it like any other planting. A split never overfills a block and never puts a crop where its rotation, keep-apart or pollination rules already say no.
- Parts of one split stay linked so the farmer sees one seed lot planted in N beds, both in the wizard and on /plan, and the seed set aside through `drawExpected` adds up to the lot exactly once.
- The deterministic engine does the split. Claude's `areaShare` proposals for shared beds are checked by the same validator, and any proposal that leaves seed unplaced while picked blocks have room falls back to the engine's plan, tagged `fallback`.
- Leftover is reported only when every picked block is full or ruled out, and the message says which.
- A farmer who would rather keep a crop in one bed can say so, and the old single-block behaviour comes back for that crop.

The decider rules on the order blocks are filled in (largest free space first, nearest first, or the farmer's pick order), how the link between parts is stored (a shared group id on the existing planting rows is preferred to a new table), and how the wizard shows a split.

### The planning wizard's AI paths under end-to-end test

The AllocationWizard's AI chat send, "Apply anyway" and the partial-failure commit path are covered only by component tests, because e2e runs with no Anthropic key and nothing can trigger them deterministically. Add a fixture Claude for the e2e preview server only, behind the same double gate the degree-day fixture uses (`E2E_...=1` plus `ENABLE_DEV_ROUTES=1`, see `lib/ipm/pestModel.fixtures.ts`), so it can never answer in production. It plugs in below `aiTry()`, so the guard, the budget and the provenance tags run exactly as they do with a real key. The answers are canned and recorded from real response shapes. With it in place, write Playwright specs for the chat send (a refined plan comes back tagged `ai`), "Apply anyway" over a validator warning, and a commit where some plantings save and some fail, with the farmer told which. The existing no-key specs must keep passing unchanged.

### What the code does today (the facts the rulings start from)

- `planFieldLayout` already loops one counted seed over several field blocks (`tryPlace` calls `bestBlock` until the seed is placed or no block clears the floor). Pass B drops blocks that score below 0, so a seed can be reported as left over while a picked block still has room.
- `planLayout` runs fields first and sends to the beds only seeds that appear in `onFields.unplaced`, but it passes the **original** seed, not the remainder. A seed that partly fitted on fields is offered to the beds at its full quantity, so the same plants can be placed twice. This is a conservation bug.
- `packSharedBeds` spills a counted seed over several beds, but each bed is capped at a fair split with other contenders and anything still left after the ranked beds is silently dropped: a seed with `placed > 0` is never reported as left over.
- Rotation, keep-apart, sun and same-block cross-pollination are only score terms in the engine. The AI validator hard-rejects only `companionBadHere`.
- The commit path posts one planting per row. The undated path apportions seed with largest remainder; the scheduled path rounds each row on its own, so the seed drawn can differ from the lot quantity. A row that failed on the client may have saved on the server, and nothing stops a second post from saving it again.
- "Apply anyway" swaps in Claude's rejected plan but leaves `meta.fallback = 'engine-only'`, so the rows and the committed plantings are tagged `fallback` although the plan came from Claude.

## Protected space preference (#797)

The planting engine used to know nothing about greenhouses or high tunnels, and both its capacity-fit score and its "more room" tie-break favour the biggest bed. On the Willow Run demo farm each 4 x 64 ft tunnel bed is four times the size of a 4 x 16 ft garden bed, so a space-hungry crop such as Delicata winter squash ranked the tunnel first and landed there.

Ruling (the most conservative option that uses only data the app has):

- A block in a greenhouse Area (any structure: glass, poly, high tunnel, caterpillar) is protected space. `protectedBlockIds` in `lib/layout/bedSharing.ts` derives it from the Area kind; `buildAllocationInput` and `buildPlanInput` pass it to the engine.
- No crop plugin field says a crop needs protection, so the preference applies to every crop. A rule from days to maturity against the frost-free season was considered and rejected: it misreads transplanted, hardy and overwintered crops and would be an agronomy inference with no source.
- It is a ranking nudge only (`PROTECTED_SPACE_NUDGE`, equal to the capacity-fit weight, so a tunnel's extra room alone never outranks an open block that suits the crop). It is never compared against a score floor and never a rule-out, so protected space is used as soon as open ground is full or ruled out, an all-protected selection plans exactly as before, and the Phase 35 leftover rule (no seed left while a picked block has room) is unchanged. The validator does not check it.
- Claude sees `protected=Y` on those blocks with the same soft preference, and is told never to leave seed unplaced because of it. An engine row on protected space says so in its Why line (`wizard.engine.why.protected`, English and Spanish). The farmer can still put any crop in a tunnel by hand or ask for it in the chat.
