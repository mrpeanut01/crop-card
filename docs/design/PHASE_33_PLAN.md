# Phase 33 plan: document vault, organic records, manure carryover and follow-ups

Status: planned 2026-10-01. Nothing in this phase has shipped. Sources: the "Deferred" section and Decisions table of [`PHASE_32_PLAN.md`](PHASE_32_PLAN.md), CLAUDE.md, and the code on `main` at `82a4c11`. Every open design question is ruled in "33 rulings". Every number or regulation the plan needs from a primary source is a task in [`docs/research/phase-33-research-prompt.md`](../research/phase-33-research-prompt.md), and is marked "(verify)" below until that task lands.

## Why this phase

Phase 32 deferred three items with a clear order. The document vault and the organic certification pack were marked "Phase 33 first". The aminopyralid manure chain was marked "Phase 33" because it is a real way to kill a garden. Phase 33 builds them in that order, then picks up the follow-ups with the most daily value: record cards that open offline, a live task timer, dragging a bed preset onto the garden designer, fresh /today and /plan visual baselines and a sourced Care Guide.

The vault comes first because two later sprints need it. A certifier pack is much more useful with the organic certificate, seed search evidence and lab reports attached, and the soil test row has carried an unused `document_id` since migration 0060. The vault also takes journal and animal photos out of SQLite, where they are stored as data URLs today. That makes the database smaller, so Litestream restores and cold starts get faster too.

Organic records come second. CropCard already knows most of what an organic inspector asks for: every input applied, every planting, every harvest, every animal treatment. What it lacks is a place to say which Areas and animals are under organic management, where harvests went, how seed was sourced, and one export that gathers it all. The pack reports facts and owner-entered statuses. It never certifies anything, and it never shows a status the app does not track.

The manure chain comes third. The kernel already knows which pesticide labels say manure from grazing animals can carry the herbicide (`grazingRestrictions.manureCarryover`), and the grazing kernel already knows which animals stood on which treated Area and when. Phase 33 follows that manure into a pile or compost batch and warns before it is spread where it can hurt a crop. Prussic acid and nitrate stay advisory, now backed by forage test entry and sourced crop flags.

## Ground rules for every sprint

These carry over from Phase 32, with three additions for this phase.

- **Numbers and rules need sources.** Every regulatory duration, threshold, carryover window and care tip ships with a source entry (`url`, `publisher`, `date`, `quote`). A value with no verified source is left out, and the UI shows only the underlying facts (dates, products, records). Nothing in this plan's "(verify)" list has been checked against a primary source; the research brief is on the critical path for 33B and 33C.
- **Report facts, never certify.** The organic pack, the carryover chain and the forage advisory say what the records show and who entered what. They never say a field, animal, batch or forage is "organic", "safe" or "clear" on the app's own authority. Owner-entered statuses are labelled as owner-entered.
- **Assist, never gate (Invariant 7) and the kernel stays closed (Invariant 1).** Nothing in Phase 33 adds a safety-kernel rule. `RULES_VERSION` stays at 0.7.1. Organic, carryover and forage logic lives outside `lib/safety/` (Q-ORG-WARN). If research later justifies a gate, it is a separate ruling and a kernel change with its own version bump.
- **Tenant isolation (Invariant 6).** Every new table is branded with `tenantScoped(...)`, has `owner_id` with an owner-leading composite index, is in `tenant.crossTenant.test.ts`, is wiped with the farm and is in the GDPR export. Every id in a request body is checked in `lib/server/foreignRefs.ts`. Stored file bytes get their own byte-level cross-tenant test.
- **The hold guard (C-35).** No new table is a `// @hold-fact` table. Any write that touches an existing hold-fact table (`animals`, `record_deletions`, `harvest_events` and the rest in `hold-fact-tables.json`) either goes through `guardedHoldWrite` or lives in a repo function marked `@hold-exempt: <reason>`, and `gen:tables` is rerun so the drift tests pass. Any new `record_deletions.record_kind` gets a `FACT_EFFECT` entry of `none`.
- **Offline.** New queue kinds are tagged with the Owner, follow the `__unassigned__` fail-safe, replay through `withClientRecordId` plus `writeRecord()`, and join the fake-indexeddb property test. Dexie moves from v5 to v6 once, in 33A, with every Phase 33 store and kind declared up front.
- **OpenAPI.** Every new endpoint keeps its Zod schema in a client-safe `lib/**/apiSchemas.ts`, so the drift test covers it.
- **Season close-out.** `SEASON_CLOSED` never gates documents, organic status entries, amendment batches, forage tests or time entries. Harvest dispositions follow the harvest record rules and do take the gate. Each exemption has a test.
- **Glove operation.** Every new action button is at least 48 dp. Every new page stays free of horizontal overflow at 375 px under the existing e2e guard.
- **Performance.** Measure /today query count and CPU on `main` at each sprint's branch point and again before merge. A regression over 20% blocks the merge. The vault endpoints never buffer a whole file in memory.

## 33A: Document vault

**Goal.** Give each farm a private, size-capped file store that never leaks bytes across Owners, wire it to soil tests, move inline photos into it, and make it part of the GDPR export and the farm wipe.

### Features and MVP scope

1. **Phase 33 schema PR.** Migrations 0081 to 0083, the `tenantScoped` brand on every new table, cross-tenant fixtures for each one (extend `lib/db/phase32.fixtures.ts` into a `phase33.fixtures.ts`), `foreignRefs.ts` checkers (`assertDocument`, `assertHarvestEvent`, `assertAmendmentBatch`, `assertHayCutting`), the GDPR export sections and farm-wipe entries for every new table, and the Dexie v6 bump with the `recordCards` and `taskTimers` stores and the `harvest-disposition` and `time-entry` queue kinds declared but not routed.
2. **Storage backends.** One interface in `lib/server/vault/store.ts` (`put(stream, key)`, `get(key)`, `delete(key)`, `deletePrefix(prefix)`, `list(prefix)`), with two backends:
   - **Azure Blob** in production, in a new private `documents` container in the existing storage account (`infra/azure/main.bicep`), signed with the SharedKey helper already in `apps/web/scripts/lib/azureBlob.mjs` (extended with Put Block, Put Block List, streamed Get, Delete and List). Uploads stream in 4 MB blocks.
   - **Local filesystem** in dev and tests under `VAULT_DIR`.
   - Production with no blob configuration turns the vault off and says "Document storage isn't set up yet". It never falls back to the container disk, which is wiped on every restart (V-02).
3. **Upload.** `POST /api/documents` takes the raw file as the request body, with `kind`, `title` and optional link fields in the query. It requires `Content-Length`, refuses anything over the per-file cap (20 MB) or over the farm's plan cap, sniffs the type from the first bytes and ignores the client's declared type, and accepts only PDF, JPEG, PNG, WebP and CSV (V-05). It strips EXIF and XMP from JPEG, and text chunks from PNG, before storage (V-07). Storage keys are `owners/<ownerId>/<documentId>`, with no part taken from the file name (V-04).
4. **Serving.** `GET /api/documents/[id]/file` looks the row up through `withTenant`, checks access for the subject it is linked to (V-09), and streams the bytes with the stored type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'; img-src 'self'; style-src 'unsafe-inline'`, `Cache-Control: private, no-store` and `Cross-Origin-Resource-Policy: same-origin`. Images are served `inline`; PDF and CSV are served as `attachment` (V-06). A missing, deleted or foreign id is always 404, with an identical body.
5. **Caps and usage.** Plan caps from Q-VAULT-CAPS (Free 100 MB, Grower 1 GB, Farm 5 GB) join `lib/billing/plans.ts` as `storageBytes`. Uploads are checked against a live `SUM(byte_size)` over the farm's documents, so a burst cannot overshoot. Reads are never blocked. `storageUsage.ts` adds a `documentBytes` part to the nightly cached total shown on /settings/documents and /admin/owners.
6. **Links.** `document_links` attaches one document to one or more subjects: `soil-test`, `stock-lot`, `animal`, `animal-group`, `animal-health`, `field`, `block`, `harvest-event`, `ledger-entry`, `organic-status`, `amendment-batch`, `forage-test` or `farm`. `soil_tests.document_id` points at the lab report and replaces the free-text `report_pdf_url` in the sheet (the old column is kept and still shown when set).
7. **Photo migration.** `runDbMaintenance` moves journal and animal photos out of their `photo_ref` data URLs into the vault in batches of 100 per run, sets `photo_document_id`, then clears `photo_ref` in the same transaction as the link (V-11). Reads accept either column during the move. New journal and animal photos go straight to the vault once it is configured. The animal photo write sits in a repo function marked `@hold-exempt: photo columns carry no hold facts`. User avatars are global, not farm data, and stay where they are.
8. **Delete and wipe.** An owner can delete a document. The row keeps its metadata with `deleted_at` and `deleted_by`, the bytes are deleted at once, and every link shows "Deleted on <date> by <name>" (V-12). The farm wipe deletes every row and queues `owners/<ownerId>/` in `blob_deletions`; maintenance deletes the prefix, retries on failure and sweeps blobs with no row after 24 hours (V-13). The privacy copy says plainly that backup copies in storage expire within 14 days.
9. **GDPR export.** `export.json` lists every document's metadata, including `sha256`. A new `GET /api/account/export.zip` streams `export.json` plus every live document under `documents/<id>-<safe name>` through a hand-rolled store-only ZIP writer with ZIP64 (`lib/server/zip.ts`), so a 5 GB farm never sits in memory (V-15). The same writer serves the 33B pack.
10. **UI.** `/settings/documents` (owner only): list by kind, usage meter against the plan cap, upload, delete. `components/documents/DocumentAttach.svelte` (pick a file or an existing document) on the soil test sheet first; 33B and 33C reuse it.

- **Data model:** migration 0081.
- **Card kinds:** none new. The soil test Card shows "Lab report attached" with an "Open when online" link; vault files are never in the offline snapshot (V-16).
- **Offline queue kinds:** declared only. Uploads are online only.
- **Safety kernel:** no change.
- **AI touchpoints:** none. Soil lab OCR stays deferred.
- **Plan tiers:** the vault is on every plan; only the cap differs.

### Acceptance

- **Unit:** every new table is in the cross-tenant test. Sniffing tests cover each allowed type, a PDF renamed `.jpg`, an HTML file renamed `.pdf`, an SVG, a polyglot JPEG with an HTML tail (served with the sandbox CSP and `nosniff`, never as HTML), a zero-byte file and a truncated upload. EXIF strip tests assert no GPS tag survives. ZIP writer tests read the output back, including a ZIP64 case built from a sparse stream.
- **Byte-level cross-tenant property test** (`vault.crossTenant.test.ts`, filesystem backend): over random owners and random sequences of upload, link, list, read, delete and wipe, a request in Owner B's context never returns a byte of any file Owner A uploaded (each file carries a unique random marker that is searched for in every response body and in B's export ZIP), every storage key starts with its own Owner's prefix, a wipe of A leaves B's files byte-identical, and a guessed or replayed id from A answers 404 for B.
- **Header test:** every response from the file route carries the sandbox CSP, `nosniff`, `no-store` and the right `Content-Disposition`.
- **Quota test:** an upload that would cross the cap returns 413 `STORAGE_FULL` and stores nothing; reads still work for a farm over its cap.
- **Migration test:** a seeded farm with journal and animal photos ends with every photo in the vault, `photo_ref` empty, byte-identical images and a smaller database file.
- **e2e:** upload a lab PDF from the soil test sheet, open it, delete it and see the "Deleted" line; the GDPR ZIP contains the file; a helper cannot open an owner-only document.
- **Persona, farm:** the owner attaches last spring's Virginia Tech soil report and finds it from the soil test Card.
- **Persona, garden household:** a gardener's journal photos keep showing after the move, and /settings/documents shows how much of the 100 MB they use.

### 33A rulings

Binding for every 33A cluster (2026-10-01). Where a ruling differs from the plan above, the ruling wins and its row says why. 33A adds no agronomy or animal number, no safety-kernel rule and no AI call; `RULES_VERSION` stays 0.7.1.

Code facts these rulings rest on (checked on `p33-plan` at `334692f`):

- `infra/azure/main.bicep` turns on blob versioning and 14-day soft delete for the whole storage account, and its lifecycle rule keeps previous versions 30 days.
- adapter-node reads `BODY_SIZE_LIMIT` with a default of 512 KB, and nothing in the repo sets it, so a 20 MB upload is refused before the route runs today.
- `runDbMaintenance` runs at most once per 24 h.
- `syncQueue.endpointFor` falls back to the herbicide endpoint for any kind it does not know.
- `PHASE_32_RECORD_KINDS` no longer exists; every Phase 32 kind is routed.
- `FACT_EFFECT` in `lib/safety/holdLedger.ts` is keyed by hold fact kind, not by `record_deletions.record_kind`, and has no `none` value. The hold ledger reads tombstones only for `spray`, `insecticide` and `fungicide`.
- `SetupSoilTest.svelte` has no report URL field; only the API takes `reportPdfUrl`.
- `GET /api/account/export.json` uses `requireUser`, so a helper can call it.
- `wipeAllData` is a series of deletes and is not one transaction.
- Journal and animal photos arrive as JPEG data URLs (300 KB cap, `sanitizePhotoDataUrl`), including through the offline `journal` queue kind.

## 33B: Organic records and certifier pack

**Goal.** Let a certified or transitioning farm keep its organic records in CropCard and hand an inspector one pack, without the app ever claiming a status it does not track. Add the animal section to the year summary and an animal treatment log export that any inspector can use.

### Features and MVP scope

1. **Organic status per Area and block.** An append-only `organic_status_events` history per field or block, entered only by the owner: `organic`, `transitioning` or `not-organic`, an effective date, the certifier's name and an optional certificate from the vault. A block with no entry inherits its Area's; a subject with no entry at all has no organic status and shows none (O-01). The status reads "Organic (owner-entered, effective <date>, certifier <name>)", never just "Organic".
2. **Facts beside each status.** For each block, the page lists what the records show for any window the owner picks, default the last 36 months (verify, 7 CFR 205.202(b)):
   - every application of an input whose library entry is not marked organic-allowed, split into "marked not allowed" (an explicit `certifiedOrganicAllowed: false`) and "not marked either way" (O-04);
   - every planting from a seed lot recorded as `treated`;
   - the date of the last such input on file.
     The derived "earliest date the land could qualify" line appears only once research Task R1 verifies the 205.202(b) wording, and even then reads "By these records, 36 months after <date> is <date>. Your certifier decides." (O-03).
3. **Input compliance checks.** Recording a spray, insecticide, fungicide or fertility application on a block with an `organic` or `transitioning` status shows a non-blocking notice when the product is not marked organic-allowed in the library: "This product isn't marked as allowed for organic use. It will show on this block's organic record." The save is never blocked (Q-ORG-WARN). The check reads `complianceFlags` through one helper, `lib/organic/inputCompliance.ts`, which `philosophyFilter.ts` also starts using so the two can never disagree.
4. **Animal and group status, and loss after treatment.** Owners record `organic_status_events` on animals and groups the same way. `lib/organic/animalStatus.ts` reads the existing `animal_health_events` and, for each treatment of a subject with an `organic` or `transitioning` status, finds one of three outcomes:
   - **Status lost.** The product's plugin is `productKind: "antibiotic"`, or the owner reviewed the treatment and confirmed the loss. The 7 CFR 205.238(c)(1) wording behind the automatic case is research Task R1 (verify). Until it is verified, antibiotics also go to "needs review" (O-08).
   - **Needs review.** Anything else: free-text products, plugins with no sourced `organicUse` entry, and any product whose sourced entry names conditions. The owner answers once per treatment in `organic_treatment_reviews` ("Ends organic status" or "Does not end it", with a reason). Reviews lock after 48 hours.
   - **Not affected.** Only when the owner answered "Does not end it". The app never decides this on its own (O-09).
     A loss is one-way in the app: a later status entry cannot put a lost animal back to `organic` (O-10). Group treatments reach members through the existing membership history (`lib/animals/membership.ts`). Every treatment screen for an organic animal shows "Treat a sick animal. The organic rules forbid withholding treatment to keep status." with its citation, 7 CFR 205.238(c)(7) (verify) (O-11). The Animal Card shows the owner-entered status line when there is one, and nothing when there is none (O-01).
5. **Harvest dispositions.** A harvest record gets one or more dispositions: `sold`, `kept`, `donated` or `discarded`, each with its own quantity and unit, a date, an optional recipient and, for `sold`, a "sold as organic" yes or no. "Also record the money" opens the existing ledger sale flow and stores the `ledger_entry_id` (Q-SALES-SCOPE). Dispositions take the 48 h lock and tombstones (Q-ORG-DISP-LOCK). They are not hold facts and never change a hold (O-13). Marking a sale "sold as organic" from a block whose status at harvest was not `organic` shows a notice and still saves. Dispositions replay offline as the `harvest-disposition` queue kind.
6. **Organic seed sourcing.** A seed stock lot gains `seed_organic_status` (`organic`, `untreated`, `treated` or `unknown`), a list of sources checked (`[{ supplier, checkedAt, result }]`, Q-ORG-SEED-FIELDS), a commercial unavailability note, and vault documents as search evidence. The seed sourcing list flags non-organic lots with no sources checked as "No search on file". The app does not judge whether a search was enough, which is the certifier's call under 7 CFR 205.204 (verify).
7. **Certifier pack.** `GET /api/organic/pack.zip?from=&to=` streams a ZIP from the 33A writer with a PDF summary and one CSV per section:
   - farm, Areas, blocks and animals with their owner-entered status history;
   - an activity log of every application, planting, seed start, fertility application, amendment spread, harvest and hay cutting in the window;
   - an input list with EPA registration numbers and the library's compliance flags exactly as stored, each tagged with its provenance;
   - seed sourcing;
   - the animal treatment log (item 9);
   - harvests with their dispositions and linked sales;
   - an index of linked documents, and optionally the documents themselves.
     Every page and CSV header reads "Prepared from records kept in CropCard. This is not a certification." Records saved late carry their existing late label (G2). The pack is free on every plan.
8. **Year summary animal section.** `yearSummary.ts` gains an `animals` section: head count by species at the start and end of the year, arrivals and departures by status, treatments by product with the subjects treated, production totals by food and use, and holds that covered a declared food or sale (from the hold ledger's covered set). It shows in the /records "Year in review" and the year summary PDF only when the farm has animals.
9. **Animal treatment log export.** `GET /api/animals/treatments.csv` and `.pdf` with `from` and `to`: date, subject, species, product, approval number, lot, dose and route, given by, vet, label use, withdrawal per food with its clear date and source, locked, voided or owner-corrected, and organic review outcome when there is one. Inspectors and owners can download it. It is the same table the pack uses.

- **Card kinds:** none new. The Area Card and Animal Card gain the owner-entered status line; the Planting Card gains nothing.
- **Offline queue kinds:** `harvest-disposition` is routed. Status entries, reviews and seed sourcing are online only.
- **Safety kernel:** no change.
- **AI touchpoints:** none. The Organic System Plan generator stays deferred.
- **Plan tiers:** all free.

### Data model

- `organic_status_events`: `id`, `owner_id`, `subject_type` (`field`, `block`, `animal`, `group`), `subject_id`, `status`, `effective_at`, `certifier`, `note`, `created_by`, `created_at`. Index `(owner_id, subject_type, subject_id, effective_at)`. The current status is the latest `effective_at`, then the latest `created_at`.
- `organic_treatment_reviews`: `id`, `owner_id`, `health_event_id`, `outcome` (`status-lost`, `not-affected`), `reason`, `created_by`, `created_at`, `locked_at`. One live review per treatment.
- `harvest_dispositions`: as in the migration map. `quantity_hundredths` and `unit` are separate from the harvest's free-text quantity.
- `stock_lots`: `seed_organic_status`, `seed_sources_checked_json`, `seed_unavailability_note`.
- `record_deletions.record_kind` gains `harvest-disposition`, with `FACT_EFFECT` `none`.
- Plugin schema: `animalHealthPluginSchema` gains an optional `organicUse` (`{ status: "allowed" | "allowed-with-conditions" | "not-allowed", citation, conditions? }`), sourced in `animal-health-sources.json`, filled only by research Task R2.
- New source file `apps/web/scripts/nop-sources.json` for every regulatory rule the code reads (R1), with a coverage gate.

### Acceptance

- **Unit:** status projection tests cover inheritance from Area to block, a block override, a subject with no entry (no status shown), and same-day entries. `animalStatus` tests cover each outcome, a group treatment reaching members, a member joining after the treatment (not reached), the one-way loss, and the "needs review" fallback while `nop-sources.json` lacks a verified 205.238(c)(1) entry. `inputCompliance` is one table shared with `philosophyFilter`, and a test pins that the two agree on every shipped plugin.
- **Coverage gate:** a rule constant in `lib/organic/` with no verified entry in `nop-sources.json` fails CI, and so does an `organicUse` with no source.
- **Hold guard:** dispositions write no hold-fact table; the tombstone function is `@hold-exempt` and `gen:tables` shows no drift.
- **Cross-tenant:** the three new tables, and a pack built for B, never contain A's rows.
- **e2e:** an owner marks a block transitioning, records a non-allowed fertilizer and sees the notice and the fact line; a helper records a disposition offline and it replays once; an inspector downloads the pack and the treatment log; a garden household with no organic status sees no organic chrome anywhere.
- **Persona, certified farm:** the owner builds the pack for last season and every section an inspector asked for in the persona script is present, with no line that reads as certification.
- **Persona, homestead with hens:** a hen treated with a dewormer shows "needs review" until the owner answers; the treatment log CSV opens in a spreadsheet with one row per dose.

### 33B rulings

Binding for every 33B cluster (2026-10-01). These rulings fill the gaps a builder would otherwise guess in the 33B section above. Where a ruling differs from the plan, the ruling wins and its row says why. The plan's own "33 rulings" (O-01 to O-16, Q-ORG-\*, Q-SALES-SCOPE) still stand.

Code facts these rulings rest on (checked on `p33b` at `32034b7`):

- Migration 0082 already created `organic_status_events`, `organic_treatment_reviews` (unique on `owner_id, health_event_id`, FK to `animal_health_events` with `ON DELETE CASCADE`), `harvest_dispositions` (FK to `harvest_events` with `ON DELETE CASCADE`, FK to `ledger_entries` with `ON DELETE SET NULL`) and the three `stock_lots` seed columns. They are in the GDPR export (`accountExportSections.ts`), the farm wipe (`admin.ts`) and the cross-tenant fixtures (`phase33.fixtures.ts`). `record_deletions.record_kind` already lists `harvest-disposition`.
- `FACT_EFFECT` is keyed by hold fact kind and has no `none` value. Every hold loader filters `record_deletions` by an explicit kind list (`spray`, `insecticide`, `fungicide`, `animal-health`, `animal-production`, `animal-status`), so a `harvest-disposition` tombstone is invisible to the hold ledger without any entry.
- `harvest_events` and `record_deletions` are hold-fact tables; `stock_lots`, `ledger_entries` and the three new tables are not.
- Health deletes are hard deletes plus a tombstone whose snapshot is `{ event, dosed }`. A void deletes with `dosed: false`. A review row cascades away with its treatment.
- Harvest ids are server generated; a harvest queued offline has no id until it syncs.
- `ledger_entries` is owner only (F2-1, `requireMoneyReader`/`requireMoneyWriter`) and already carries `harvest_event_id`. The existing sale flow is `/finance/new?kind=income&harvestEventId=&cropId=` (`recordSaleHref`).
- `complianceFlags` on the 245 shipped input plugins: 5 fertilizers carry `certifiedOrganicAllowed: true` with `omriListed: false` (composted manures, biochar, molasses, Chilean nitrate); 4 plugins carry `certifiedOrganicAllowed: false` yet pass the planner's `organic-transitioning` branch (cottonseed meal, soybean meal, K-Mag, Met52 EC). Fertilizer `organic: true` means "organic-source amendment", not "allowed under the NOP" (schema comment).
- `syncQueue.endpointForRecord` already rewrites `:id` paths for `feed-use` and `seed-start` from a payload field and strips it from the body.
- Health event kinds that carry a product are `HOLD_BEARING_KINDS` (`treatment`, `vaccination`, `deworm`).
- `canReadDocument` (A-31) lets owners and inspectors read `organic-status` documents and helpers read `stock-lot` documents; `ledger-entry` documents are owner only.

## 33C: Manure and compost carryover chain, and the forage advisory

**Goal.** Follow manure, bedding and compost from animals that grazed or ate forage treated with a carryover herbicide to the block where it is spread, and warn before it reaches a crop that herbicide damages. Give prussic acid and nitrate risk a sourced advisory and a place to record forage tests, without a gate.

### Features and MVP scope

1. **Plugin data.** `grazingRestrictions` gains two optional, sourced fields: `manureCarryoverDays` (the label's window between grazing or eating treated forage and manure that must be kept out of compost or off sensitive crops; GrazonNext HL says 3 days, verify) and `hayOffFarmRestricted` (the label limits moving hay from treated areas off the farm, verify). `farmCopyRestrictions` treats both as lengthen-only, like the other fields. Research Task R3 fills them for the five shipped plugins with `manureCarryover: true` and checks every other shipped herbicide whose active ingredient is a pyridine carboxylic acid (aminopyralid, clopyralid, picloram) for a missing flag.
2. **Batches.** An owner or helper creates an amendment batch (`manure`, `compost` or `bedding-pack`), on-farm or bought, and adds what went into it:
   - an animal or group, with the collection window (`from_at`, `to_at`);
   - another batch, for compost made from manure (any depth, cycle-safe);
   - a bought stock lot, with the supplier's statement: `says-none` ("supplier says no carryover herbicide"), `unknown` or `none-asked`.
     Hay put into feed inventory from a hay cutting stores `stock_lots.source_hay_cutting_id`, so feed use from that lot links animals to the cutting.
3. **The chain.** Pure `lib/amendments/carryover.ts` computes, for each batch, one of three states and the path that led there:
   - **May carry.** A source animal or group grazed an Area, or ate hay cut from a block, with an application of a `manureCarryover` product inside that product's grazing or hay interval, and the collection window overlaps the exposure plus `manureCarryoverDays`. With no sourced `manureCarryoverDays`, the window runs to the end of the collection (M-04).
   - **Not known.** A bought input with any supplier statement other than `says-none`, or a source whose exposure the records cannot settle.
   - **None on file.** No path found. The copy is "No carryover weed killer on file for this batch's sources", never "safe" (M-05).
     Exposure reuses the grazing kernel's stays and applications (`grazingExposure.ts` inputs through `lib/server/grazingGate.ts` loaders), read-only.
4. **Before spreading.** Recording a fertility application with a batch in the "may carry" or "not known" state on a block that holds, or has planned within 12 months, a crop in a family the synthetic-auxin class kills (`CHEMISTRY_KILL_MATRIX['synthetic-auxin'].killsFamilies`, already kernel data), or on any `garden` or `greenhouse` Area, answers 409 `CARRYOVER_CONFIRM` with the facts and the label quote. The person can confirm and save; the confirmation, the facts and who confirmed are stored in `carryover_ack_json` (M-02). Helpers can confirm too, since this is advisory.
5. **After spreading.** The Block Card and Area Card show "Got <batch> on <date>, which may carry a weed killer that harms <families>. Consider a bean or pea test before planting." Planting a sensitive crop on that block shows the same line as a hint. The line stays until the owner records a bioassay on the block or the batch (`amendment_bioassays`, result `no-damage` or `damage`) or dismisses it with a reason. A `no-damage` bioassay changes the line to "Your pea test on <date> showed no damage", and the facts stay on file (M-07). Bioassay copy cites research Task R4.
6. **Hay leaving the farm.** A hay cutting from a block with an application whose label has `hayOffFarmRestricted` shows the label quote on the /hay card. When hay dispositions arrive later, this is the hook; for now it is a notice only.
7. **Prussic acid and nitrate advisory.**
