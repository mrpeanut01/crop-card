# #870: Phase 37 small follow-ups

Waterer gallons with several targets, undo a skip, "running since" on a timer, and the garden brief's conversation kept with the brief. Closes the four 37A/37E items under "Still open after 37" in [`../PHASE_37_HERB_GARDEN_PLAN.md`](../PHASE_37_HERB_GARDEN_PLAN.md). No safety-rule change (`RULES_VERSION` stays 0.7.11), no AI call added, no new /today query (R-22), no Dexie version or queue kind change, no snapshot or export version bump.

## Decisions made while building

- **D-1 (FU870-1) A share set that does not add up is not known.** Typed shares are all or none: `PUT .../water-targets` refuses a partial set (400 `SHARES_INCOMPLETE`) or a total other than 100 (400 `SHARES_TOTAL`). If a stored set stops being complete later (a bed is deleted and its target row cascades away), the split reads "not known" with "the shares you typed no longer add up to 100%", never the size split and never a rescaled share. Shares are 1 to 100: a target that gets nothing should be taken off the timer.
- **D-2 (FU870-1) One target keeps no share.** A timer with a single kept target stores `share_pct` null and takes every gallon whatever its size, so the single-target path is exactly the old code (proven by a golden fast-check test against the pre-#870 `timerLogs`).
- **D-3 (FU870-1) The /today read now loads the whole timer.** `loadWatererRowsForAreas` reads every target of each waterer that has a target on the Areas with a crop in the ground (a subquery in the same statement), joined to each target's Area and bed size columns and to the skips. Before, a timer that watered two Areas but had plantings in only one looked like a single-target timer there and gave that Area every gallon. Still one statement (`waterAdvice.followups870.test.ts` asserts the provider stays at 5 reads or fewer; the /today budget test passes for owner and helper).
- **D-4 (FU870-1) Overlap uses the bed's current Area.** A bed that moved into an Area the same timer waters whole counts as overlapping (the target row still names its old Area). Logs still go to the Area the target row names, as before.
- **D-5 (FU870-1) The size split is shown as `fallback`.** On the equipment page each target's percent is tagged `fallback` ("Split by the size of each Area and bed") because it assumes the emitters spread water evenly by area; typed shares are `manual`. The water logs themselves stay `manual` either way. With inches per run typed, inches win on every target and the split section says so.
- **D-6 (FU870-2) Undo is online only.** `undoSkip()` in `lib/irrigation/client.ts` never queues: a skip still in the offline queue has no server id (it is removed from /records/pending instead), and a queued undo could replay after the 48-hour window. Offline, the card says "Undo needs a connection." A replay of the skip's own client record id after an undo answers as a duplicate and does not bring the skip back (endpoint test).
- **D-7 (FU870-2) Where skips show.** The /today watering card lists the skips of the Area's timers in the advice window (a week back, eight days ahead) as "Drip timer skipped Wed, Oct 14 at 6:00 AM (it didn't run)." with Undo when the viewer may undo it; the equipment page lists the same window under "Skipped runs". The skip ids, reason, author and save time come from the existing /today waterer read (no new query); `TodayAdviceContext` gains `viewerId`. Inspectors get 403 `READ_ONLY` (the hooks layer already refuses their writes); other members `NOT_YOURS` or `TOO_LATE`, all with `askOwner: true` and a message ending "Ask the owner."
- **D-8 (FU870-3) What a stored turn is.** A turn is stored only when it counts toward the 8 (Claude was asked and answered, usable or not): `{ question, reply, provenance, at }`. `reply` is Claude's filtered reply exactly as returned to the page, or null when the page showed the form's own reply (an answer that failed the checks, or a reply the spray filter emptied); a null reply renders in the viewer's language, so no app text is stored. Spray questions, no-key, over-limit, slow and turn-limit answers store nothing and leave earlier turns as they were. `transcript` is optional on the brief schema, so briefs saved before #870 still parse.
- **D-9 (FU870-3) Read-only when Claude is off.** A returning owner whose farm no longer has Claude on sees "Your earlier conversation" read-only (no form). The page sends at most the last 16 lines as history, since the server's schema caps it there.
- **D-10 (FU870-4) Running since is a day in the farm zone.** It counts from midnight of that day in `farmTimeZone()` and must not be after today there (400 `IN_THE_FUTURE` on create and edit). It is not part of `sameProgram`, so changing it never moves `activeFrom`; sending the schedule without it clears it.

## As built

- **Schema.** Migration 0096 adds `equipment_water_targets.share_pct` (nullable integer). The table was already tenant-scoped, in the cross-tenant test (the Phase 37 fixture row now carries a share), the farm wipe and the export (`watering.waterTargets` reads every column, so `sharePct` is exported). No migration 0097 was needed.
- **Pure logic.** `lib/irrigation/schedule.ts`: `gallonsSplit` (`single | typed | size`, or not known for `no-size | overlap | shares`), `targetsOverlap`, `targetGallons`, exported `runGallons`, `countsFromMs` and `expandRuns` reading `runningSince`; `timerLogs` gives each target its own gallons. `lib/irrigation/skipUndo.ts` (`skipUndoVerdict`, `SKIP_UNDO_WINDOW_MS`). `lib/garden/brief/schema.ts`: `briefTranscriptTurnSchema`, optional `transcript`, `briefForViewer`, `transcriptLines`.
- **API.** `DELETE /api/irrigation/skips/[id]`; `PUT /api/equipment/[id]/water-targets` takes `areaShares` and `blockShares`; equipment POST and PATCH check `runningSince`; `GET /api/garden/brief` and the /plan/brief loader strip `transcript` for helpers and inspectors; `POST /api/garden/brief/chat` appends counted turns. OpenAPI entries for `/api/irrigation/skips`, `/api/irrigation/skips/{id}` and `/api/equipment/{id}/water-targets` (37E had not registered them), with drift-test rows for the two request schemas.
- **UI.** `AdviceCards.svelte` skip lines with Undo; `WatererEditor.svelte` "How the gallons split", "Type each one's share of the gallons", "Running since (optional)" and "Skipped runs" with Undo; `BriefChat.svelte` `readOnly`; /plan/brief starts from the stored turns. Every new string is in `catalogs/{en,es}/herbsg.ts`; the old `herbse.editor.gpmHint` is no longer rendered (replaced by `herbsg.editor.gpmHint`) and can be removed with the next herbse edit.
- **Tests.** `lib/irrigation/split.test.ts` (golden single-target test against the old code, fast-check properties of the split, the depth under the size split, unknown still blocking "water", running since), `lib/server/waterAdvice.followups870.test.ts` (whole-timer split through the /today read, typed shares, skip lines and Undo rights in English and Spanish, one read, tenant isolation), `routes/api/irrigation/skips/followups870.endpoint.test.ts` (undo rights, 48 hours, 404 across farms, replay after undo, shares validation, running since), `routes/api/garden/brief/brief.transcript.test.ts` (stored exactly as shown, owner only on the API and the page, nothing on no-key or spray, the form reply as null, 8 at most, DELETE, export and snapshot), and e2e `tests/e2e/phase37-followups.spec.ts`.
